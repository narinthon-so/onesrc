# Claude review of the product direction and tool research

Date: 2026-11-01. Status: review, not an adoption decision.

Reviews [the product discussion](2026-10-30-product-direction.md) and
[the Docker deep dive](2026-10-30-docker-mcp-gateway.md). Tool claims were
rechecked against current docs and READMEs. No tool was installed or run. Local
facts come from read-only checks of this machine. `thv` and the `docker mcp`
plugin are not installed.

## Verdict

Do not build a gateway. The first verdict was to test ToolHive and, if it
passed, shrink onesrc to instructions plus drift. **The PoC (end of this file)
failed that test.** ToolHive drops comments from Codex's TOML, writes the
Antigravity IDE path rather than the agy CLI one, and loses executable bits on
skills. Revised: keep onesrc's config and skill writes, and use ToolHive vMCP as
an optional MCP runtime behind them.

## Answers to the brief's questions

1. **Gateway, config management, or both?** Both exist in the sketch, but only
   parts remove setup. A gateway removes repeated MCP and credential setup. Skills
   and instructions are still files in each client, so they stay config
   distribution.
2. **"Standard format"?** Recommended reading: MCP tool calls with backend-specific
   schemas, and no `email.send` facade. A facade only pays off when providers get
   swapped, and nothing shows that need. This is Bale's call; see "Open".
3. **Can an existing tool do email, PR and skills on all three agents?** On paper,
   ToolHive can route to email and GitHub MCP servers and install skills. Nothing
   has been demonstrated. PRs may not need a hub at all, as these agents have a
   shell and `gh`.
4. **Skills loading?** Install into native directories. Native runtime loading
   isn't available in these clients, per the matrix. Bridges such as `skillhub-mcp`
   expose skills as tools, which loses native discovery. Portability of
   agent-specific references remains unsolved either way.
5. **Which earlier decisions survive?** Import-before-sync, conflict blocking,
   whole-bundle comparison and copying skills unchanged all remain sound for
   whatever still writes files. Reuse `inspect`, `status`, `redact` and the
   adapters' read paths. Defer M2 (MCP writes) and the skill half of M1 until the
   test reports. Only the instruction half of M1 is safe to continue now.
6. **Credentials?** In the gateway process, if adopted. That also settles most of
   the open `secrets.env` question: agents would need a gateway connection rather
   than provider secrets. OAuth stays per-agent for anything not routed through it.
7. **Authorization, failures, retries?** No tool here establishes exactly-once
   sends or per-action approval. Don't build a workflow engine. Rely on each
   agent's own tool-approval prompt, and treat email send as not safely retryable.
   Duplicate PRs fail at GitHub for the same head and base, per its usual behavior;
   the test should confirm that through MCP.
8. **Is there differentiated value?** A narrow one: user-level instructions across
   the three agents, plus drift reporting with shadow detection. That may be small
   enough for a dotfiles script. Decide after the test, and don't assume a product
   survives.

The hub's `cli` box deserves dropping for now. Agents already run CLIs directly,
and Bale's global rule prefers CLI over MCP because MCP schemas cost context. A
wrapper would add schema cost to reach a tool the agent can already call.

## Smallest next validation

Proposed, not run. Use a disposable `HOME` throughout: `~/.claude.json` and
`~/.codex/config.toml` must not be touched by this test.

1. Install a pinned `thv`. Docker 29.5.0 is present.
2. Seed the fixture home with commented, hand-edited configs for all three agents.
3. Register all three clients and run one harmless MCP server. Diff every written
   file. **Pass:** comments and hand-added entries survive, and Agy's written path
   is one that Agy actually reads.
4. Install a skill with a helper script and executable bit into all three.
   **Pass:** the whole bundle arrives, and each agent discovers it.
5. Connect each agent to one `thv vmcp serve` endpoint, then list and call a tool.
6. Only then test a real PR and email, in authorized test destinations.

**If steps 3 or 4 fail:** comments lost or wrong paths leave onesrc's ownership-safe
writes as a real differentiator. Continue M1 and M2 as designed, and use ToolHive
or Docker only as a runtime behind them.

commented, hand-edited configs. Agents: Claude Code 2.1.316, codex-cli 0.163.0,

Side effect: one unsandboxed `thv version` created ToolHive state dirs in the
real home before the sandbox was set; they were removed. No agent config in the
real home was changed.

### What this means

Steps 3 and 4 failed, so the fallback in "Smallest next validation" applies:
ToolHive's client writer is not a replacement for onesrc's ownership-safe
writes. Its runtime is useful. A split that fits the evidence:

- **vMCP (ToolHive) as the optional MCP runtime.** Servers and credentials are
  configured once there.
- **onesrc writes the agent side.** That is one `vmcp` entry per agent (or
  direct entries without vMCP), skills with modes preserved, and instructions,
  including the list of available CLIs. Use the agy CLI path, not the IDE path.

Do not use `thv client register` or `thv skill install` against the real home.

### Reading

- On paper, **rulesync** covers the most: all three agents with `agy` separate
  from the IDE, all three kinds of config, global mode, dry-run and check, and
  it is actively maintained. The questions ToolHive failed on are unanswered:
  hand-added entries, Codex TOML comments, and secret references.
- **agent-sync** matches onesrc's design most closely (neutral hub, `agy`
  named, `${VAR}`, managed blocks, keeps tool-only MCP), but it has one star.
- **amtiYo/agents** now has a global mode, so the "project-centric" gap in
  DESIGN.md's prior art is out of date. Its `agy` path is unconfirmed.
- No tool documents comment-preserving edits to Codex TOML. That claim is
  onesrc's strongest remaining differentiator, and it still needs a test
  against each candidate.

### rulesync 43.4.1: source reading (Claude + Codex scope)

Bale asked (2026-11-01) for the best tool if Antigravity is left out, then
for a test of rulesync. Running it was blocked, so this comes from the
installed bundle (`dist/import-BKyt4qe5.js`), not from execution.

- **Codex `config.toml`:** the `mcp` feature declares `replace-owned-keys` with
  `ownedKeys: ["mcp_servers"]`, and TOML is written back with `smol-toml`
  `stringify`. Its own doc comment says only JSONC files are edited in place
  ("those files carry no comments", which is wrong for TOML). Result: the whole
  `mcp_servers` table is replaced by rulesync's list, and comments and
  formatting in the file are lost. Other top-level keys keep their values.
- **Claude `~/.claude.json`:** `{ ...existing, mcpServers: rulesync's list }`
  with `JSON.stringify(…, null, 2)`. Other keys are kept; `mcpServers` is
  replaced whole.
- **So rulesync owns the whole MCP list per agent.** A server added later with
  `codex mcp add` or `claude mcp add` is removed by the next `generate`
  unless it is first added to `.rulesync/`. Adopting it means one-time
  `rulesync import`, then adding MCP only through rulesync.
- **Impact on this machine is small:** the real `~/.codex/config.toml` has 110
  lines and no comments, and there are 1 (Claude) and 2 (Codex) MCP servers.

Skills, instructions and secret handling were not read in the source.

Reading: rulesync works as "the source owns everything". It fits if you import
one agent, merge the rest by hand into `.rulesync/`, and from then on never add
MCP servers or instructions through the agents. It does not fit a setup where
agents and hand edits keep changing the same files, which is the case onesrc
was designed for.
